# Game Art Sourcing 报告规范

## JSON 根结构

```json
{
  "title": "Game Name — 美术调研报告",
  "blocks": [
    {
      "type": "heading",
      "level": 2,
      "elements": [{"text": "🎮 游戏画像"}]
    }
  ]
}
```

## Block 类型

| type | 必填字段 | 用途 |
| --- | --- | --- |
| `heading` | `level`, `elements` | 章节标题，level 2–9 |
| `text` | `elements` | 正文 |
| `bullet` | `elements` | 无序要点 |
| `ordered` | `elements` | 有序步骤 |
| `quote` | `elements` | 章节摘要、色板、重要判断 |
| `code` | `text` | AI prompt、搜索语法 |
| `image` | `url` | 单图；建议加 `caption`, `bucket`, `source_tier`, `source_label`, `alternates` |
| `gallery` | `urls` 或 `items` | 无图注图片组；`items` 可为带分桶/备用图元数据的对象 |

Element 示例：

```json
{
  "text": "证据来源",
  "bold": true,
  "italic": false,
  "underline": false,
  "strikethrough": false,
  "link": "https://example.com",
  "inline_code": false,
  "color": 5
}
```

颜色：1 粉、2 橙、3 黄、4 绿、5 蓝、6 紫、7 灰。

## 核心输出

任何有效任务都保留以下内容，不因请求简短而删除：

1. 视觉一句话：用可观察的画面特征概括对象，不用剧情简介代替。
2. 1–3 条关键证据：绑定图片、视频时间戳或明确来源链接。
3. 最值得复用或警惕的结论：说明证据支持什么，不支持什么。

核心输出可以使用最适合当前任务的标题和顺序，不强制套固定章节。简单素材请求在核心输出后只追加素材与来源；复杂请求再叠加多个相关模块。

## 按需输出模块

| 模块 | 何时自动追加 | 主要内容 |
| --- | --- | --- |
| 素材与来源 | 找素材、press kit、截图、模型、链接 | source manifest、可直接打开的来源、素材用途与缺口 |
| 逐帧拉片 | 视频链接、逐帧、拉片、镜头分析 | 真实关键帧、时间戳、镜头/色彩/材质/UI/VFX 观察 |
| 美术风格与技法 | 完整分析，或明确点名角色、场景、UI、VFX、渲染 | 只展开有证据且与请求相关的视觉对象和技法 |
| 竞品比较 | 对比、差异、参照选择 | 使用同一维度与相近状态证据比较，分开事实与判断 |
| Visual System | 完整美术分析、系统性视觉研究、当前项目借鉴、Art Bible、生产可行性 | 按独立 reference 展开有证据的视觉身份、资产、体验、品牌和生产层 |
| Art Bible 规则 | 提炼规范、风格规则、团队执行口径 | 把观察转成逐条生产决策卡，并标出证据边界 |
| 生产可行性 | 当前项目借鉴、成本、风险、实现建议 | 用生产决策卡说明项目适配、制作成本、风险和验证建议 |
| AI prompt | 用户明确要生成参考或 prompt | 从已验证的形体、色彩、材质、光照和镜头规则生成 |
| 飞书交付 | 用户明确要求飞书，或完成标准已包含飞书 | 兼容本文件 JSON，并执行本地校验、发布和回读验收 |

## 模块选择规则

- 不让用户选择模式。根据动作词、明确交付物和项目上下文自动组合模块。
- 核心输出始终保留；根据请求自动追加相关模块；复杂请求可以叠加多个模块。
- “只找素材/链接”通常只组合核心输出与素材来源，不展开完整分析、AI prompt 或生产建议。
- “完整分析”组合核心输出，以及所有有证据支撑的相关分析模块；证据不足处写 gap，不用无关内容凑全。
- “对当前项目有什么借鉴/提炼生产规则”在相关分析基础上追加 Art Bible 规则或生产可行性，并把每条重要建议写成生产决策卡。
- 只有完整分析、系统性研究、当前项目借鉴、Art Bible 或生产可行性请求才完整读取 `references/visual-system-stack.md`。简单素材请求不要求完整读取该 reference；单点问题只展开相关层。
- 视频请求执行视频子技能定义的取帧流程，并继续使用这里的核心输出、JSON、图片和来源规则。
- 飞书只在用户明确要求或既定完成标准包含飞书时追加；不得由其他模块隐式触发。

## 证据覆盖矩阵

完整的证据坐标使用以下五轴契约：

```text
来源类型 × 游戏状态 × 时间/天气 × 镜头距离 × 进度阶段
```

每条关键图片或关键帧都尽量映射到一个五轴坐标。无法从来源确认的轴写 `未确认`，不根据画面华丽程度、角色装备或营销文案猜测。五轴使用以下取值：

| 轴 | 建议取值 | 记录规则 |
| --- | --- | --- |
| 来源类型 | `真实 gameplay 录屏`、`官方 gameplay 演示`、`官方 trailer`、`过场/叙事演出`、`开发者日志/幕后/press kit`、`商店截图`、`Key Art/Logo/UA`、`一手作者作品`、`社区/二手资料` | 视频逐帧使用结构化 `segment_type` 标明片段类型；社区与二手资料只能补充，不能替代一手证据 |
| 游戏状态 | `探索`、`战斗`、`建造/经营`、`交互/解谜`、`UI/菜单`、`叙事演出`、`胜利/失败`、`加载/转场`、`其他：<名称>`、`未确认` | 记录画面实际状态；同一证据只在确实同时展示多个状态时使用多值 |
| 时间/天气 | 时间用 `黎明/白天/黄昏/夜晚/室内受控光/未确认`，天气用 `晴/阴/雨/雪/雾/风暴/无天气表现/未确认` | 写成 `时间/天气`，例如 `夜晚/雨`；不能从调色直接推断世界时间或天气 |
| 镜头距离 | `极远景`、`远景`、`中景`、`近景`、`特写`、`UI 全屏/不适用`、`未确认` | 按主体在最终画面中的可读尺度记录；镜头角度另作观察，不混入本轴 |
| 进度阶段 | `新手/开局`、`前期`、`中期`、`后期`、`终局/通关后`、`赛季/活动`、`不适用`、`未确认` | 只采用可验证的关卡、任务、账号或官方说明；不能从高阶装备外观单独判断进度 |

可在 source manifest、图片 caption、关键帧 annotation 或独立索引中保存坐标，例如：

```text
E07 | 00:45.25 | source_type=官方 trailer | segment_type=official_gameplay
    | 战斗 × 夜晚/雨 × 中景 × 未确认
```

`segment_type` 是视频片段分类，不是第六个覆盖轴。取值固定为 `real_gameplay_capture`、`official_gameplay`、`cutscene`、`pure_promotional`、`mixed_or_unknown`。当 `source_type=官方 trailer` 时，每张关键帧必须用 `segment_type` 区分连续真实 gameplay 录屏、经官方标注或剪辑的 gameplay 演示、过场、纯宣传或混合/无法确认的片段，不能把 trailer 中所有画面都当作 gameplay 证据。

### 覆盖摘要

完整分析必须明确暴露关键 gap；项目借鉴、Art Bible 和生产可行性也必须提供与建议相关的覆盖摘要。摘要至少包含：

1. 本次使用的独立证据数量，以及五轴上实际覆盖的取值。
2. 与当前结论直接相关、但尚未覆盖的状态、时间天气、镜头或进度。
3. 来源偏差：真实 gameplay、trailer、Key Art、商店截图等各自占据了什么证据角色。
4. 结论边界：当前证据能支持什么，不能支持什么；哪些判断因此降置信度或等待验证。

相邻时间戳、同一镜头的近重复帧属于一个证据簇，不能伪装成多份独立支持。不要默认用全部可能取值的笛卡尔积计算“覆盖率”；只有事先定义了与任务相关的采样集合和分母时才报告百分比。

简单素材请求不强制填满矩阵，也不要求逐项输出五轴表；只需说明来源可靠性、素材用途和明显偏差。完整分析也不要求机械填满所有格子，但关键 gap 必须显式列出。

### 展示偏差门禁

- `Key Art/Logo/UA` 主要证明品牌承诺与营销构图，不能单独证明实时 gameplay 的镜头、材质、战斗可读性、UI 或性能表现。
- `商店截图` 是经过筛选的静态展示，不能单独证明动态状态、失败状态、长时间游玩密度或进度变化。
- `trailer` 必须区分 gameplay、过场和纯宣传片段；快速剪辑、离线渲染、特殊镜头或峰值 VFX 不能直接外推为常态体验。
- 完整分析若缺少真实 gameplay，必须把它列为关键 gap，并降低实时可读性、动态规律和生产技术结论的置信度。补充官方截图不能消除这一缺口。

## 生产决策卡

当前项目借鉴、Art Bible 规则或生产可行性请求中，每条项目型重要建议都必须独立生成一张生产决策卡。不要把角色、场景、VFX 等互不依赖的建议塞进同一张卡，也不要把方向性判断伪装成已验证规范。

固定链路为：

```text
观察 → 证据与覆盖 → 置信度 → 可转移规则 → 项目适配 → 成本/风险 → 最小验证动作
```

| 字段 | 必须回答 |
| --- | --- |
| 观察 | 分开写 `事实` 与 `推测`。事实只描述画面或来源可验证内容；推测写明尚未确认的实现、因果或动态规律 |
| 证据与覆盖 | 引用证据 ID、图片/来源或视频时间戳，并给出相关五轴坐标、已覆盖范围和关键 gap |
| 置信度 | 使用 `高/中/低`，说明依据及降级原因；不要只给等级 |
| 可转移规则 | 把竞品观察改写成与具体 IP 表皮解耦、可执行且可验收的视觉或生产规则 |
| 项目适配 | 说明目标项目的品类、镜头、玩法、资产、设备或团队约束下，保留什么、修改什么、拒绝复制什么 |
| 成本/风险 | 至少考虑人力与工期、资产/管线复杂度、性能、可读性、一致性和 IP/品牌误复制风险中与该建议相关的项 |
| 最小验证动作 | 给出能验证本卡最大不确定性的最小可执行动作，写清测试对象、目标镜头/状态、对照变量和通过/失败信号 |

`最小验证动作` 不能写成“继续调研”“做个测试”或“之后验证”。合格示例：

```text
用 1 个现有角色和 1 个现有场景制作有/无双色轮廓光两个灰盒版本，
在目标战斗中景录制各 10 秒；3 名团队成员盲测敌我识别，
若双色版无人误判且 GPU 帧时增量不超过项目预算则进入 golden sample，否则停止扩量。
```

若没有项目参数，先写最小假设和需要用户补充的约束，仍可提出可逆的小样验证；不能直接把外部游戏做法定为本项目 Art Bible 锁定规则。

## 模块完成门禁

### 核心输出

- 视觉一句话、关键证据、复用或警惕结论三项齐全。
- 每个判断都能回指图片、时间戳或来源；不能确认时标注不确定性。

### 素材与来源

- 记录标题、URL、来源类型和用途，优先官方页面与一手创作者来源。
- 游戏画像需要时包含开发商、发行年份、平台和可验证的视觉标签。
- 完整分析默认按 `key_art` 1–2、`character` 3–4、`environment` 3–4、`ui_gameplay` 2–3 组织 8–14 张质检合格图片；简单素材请求只交付用户点名的素材类别。
- L1 商店结构化接口不足时继续 L2 完整页面图集；总图少于 8 或角色/场景/UI 任一为 0 时进入 L3 视频抽帧。
- 商店标签全部翻译成中文行业术语；封面图和 gallery 一并计入全局去重。
- 找不到相关素材时明确写 gap，不用社区推测替代官方事实。
- 撰写角色、场景、UI 分析前，必须实际读取 manifest 中通过质检的本地图片；按配额自动分桶的候选须先视觉确认。

### 美术风格与技法

采用“要点 → 证据图 → 图注”的节奏：

```json
{
  "type": "bullet",
  "elements": [
    {"text": "剪影", "bold": true},
    {"text": "：宽肩、窄腰和夸张工具形成远距离识别"}
  ]
}
```

```json
{
  "type": "image",
  "url": "https://example.com/character.jpg",
  "caption": "角色全身图 — 宽肩与长工具构成三角轮廓，主色集中在上半身以保证战斗镜头可读性"
}
```

文字只提炼可观察的形体、色彩、材质、光照、构图、UI/VFX 和运动规则。世界观或剧情只在解释视觉方向时出现。

- 分为渲染管线、绘画/材质、后处理/VFX、技法总结。
- 每个判断指向画面证据。
- 无法确认时标注不确定性。
- 角色和场景使用不同技术时分别说明。

### Visual System

- 需要完整读取时，按 `references/visual-system-stack.md` 检查视觉身份、资产系统、体验系统、品牌系统和生产系统。
- 只展开与请求相关且有证据支撑的层；相关但缺少证据的内容写 gap，不为填满五层而增加无关结论。
- 每个展开层都回答玩家情绪、功能可读性、进程或状态变化，并把回答绑定到图片、视频时间戳或明确来源。

### 色板

场景小节末尾提供 3–5 个主色、2–3 个辅色和 2–3 个点缀色，并写明用途：

```json
{
  "type": "quote",
  "elements": [
    {"text": "🎨 色板\n", "bold": true},
    {"text": "主色："},
    {"text": "#D4A745", "inline_code": true},
    {"text": " 沙漠黄 · "},
    {"text": "#6B5B7B", "inline_code": true},
    {"text": " 暮色紫"}
  ]
}
```

Hex 只能引用 `scripts/image_sourcing.py` 对已落盘代表图使用 Pillow 量化得到的颜色和近似占比，并注明“画面量化取样”；禁止模型凭观察或语言描述编造 Hex。没有本地量化结果时写 `证据不足`，不要补齐色值。

### Art Bible 规则与生产可行性

- 项目型重要建议逐条使用生产决策卡，完整走完七个字段。
- 卡内区分事实与推测，并将证据 ID 或时间戳映射到五轴覆盖坐标。
- 可转移规则必须说明可直接复用、适配后复用或不应复制；项目适配写清适用的游戏类型和镜头。
- 成本/风险包含与建议相关的小团队实现路径；最小验证动作必须可执行并有通过/失败信号。

### AI prompt

- 只在用户明确提出 prompt 或生成参考需求、模块被选中时生成；仅为用户点名的角色、场景、VFX/UI 等对象各给 1–3 条完整英文 prompt，不自动补齐全套对象。
- Prompt 来自前文已提炼的形体、色彩、材质、光照和镜头规则，不直接照搬具体 IP 角色名称或构图。
- 固定结构为 `风格基底词 + [主体替换位] + Negative Prompt`；主体槽位保持可编辑，Negative Prompt 排除与证据冲突的风格、材质、构图和 UI 噪声。

### 飞书交付

- 报告保持 `{"title": "...", "blocks": [...]}` 根结构和本文件 Block 类型。
- 发布前通过 `publish_to_feishu.py --validate-only`；失败时修复 JSON，不创建文档。
- 发布后回读标题、首图和至少一个正文图片，确认内容和权限可见；不能把“文档创建成功”当成验收完成。
- 单张上传失败重试 1 次，再尝试 `alternates` 中同桶候选；全部失败时删除空图片块。
- 实际入图少于 6，或 `character` / `environment` / `ui_gameplay` 任一为 0 时，文档顶部写入 `【图源残缺：...】`，终端输出 URL、分桶数量/来源、剔除与失败原因三行回执。

## 图片规则

1. 同一 URL 在全文只出现一次。
2. 每张 `image` 都有包含视觉判断的 caption，不只描述内容。
3. 每 1–2 个重要分析点至少跟一张相关证据图；没有可靠图片就写 gap。
4. 扩展素材集只放正文未使用的图片；没有新图时写“未检索到更多不重复的高质量素材”。
5. 图片下载失败不能阻塞全部报告，但必须报告缺失数量。
6. 本地关键帧可以使用绝对路径或 `file://`，发布前确认脚本可读取。
7. 发布前过滤宽 < 480px、高 < 270px、极端比例和近纯色坏图；使用 SHA-256 + dHash 去除原图与跨分辨率近重复图。
8. WebP/AVIF/异常编码统一转为标准 JPG/PNG，超大图等比缩放并压缩到上传门限内。

## 来源规则

优先官方页面和一手创作者来源。资源链接使用完整绝对 URL，显示文本不可用 `...` 截断。

搜索链接示例：

```text
https://www.artstation.com/search?q=game+name+environment
https://sketchfab.com/search?q=game+name&type=models
```

不要把裸首页当作资产链接。

Steam 截图应从商店页 JSON 中读取当前 `full` URL，不要手工拼接。旧格式：

```text
/apps/<appid>/ss_<hash>.jpg
```

当前常见格式：

```text
/apps/<appid>/<hash>/ss_<hash>.1920x1080.jpg?t=<timestamp>
```

ArtStation 优先使用作品页、作者页和页面元数据中可访问的 cover URL。若 CDN 资源拒绝访问，保留作品页链接，不伪造图片 URL。

## 路径汇总

素材与来源模块需要本地路径或完整资产清单时，用 text blocks 输出 pipe-delimited 行：

```text
资产名称 | 类型 | 来源 | 完整链接/本地路径 | 证据用途
```
